# 按帧时伸缩的流式与上传

日期：2026-10-28。范围：呈现帧上的生成、网格和上传预算。任务槽、输入字节和输出字节硬上限保持原值。世界提交顺序未改，没有异步刷盘。

## 一、预算

窗口生成与网格仍共用一个固定线程池。线程数取可用并行度减1，给主线程留一个核心。结果夹在1到64之间，与执行器已有的工人上下限一致。低核心机器不会变成0个工人，高核心机器不再停在4。

每帧限额从4个分区、上传上限起步。主线程生成与网格安装超过8ms时，分区限额减半，最低1。低于4ms时加1，最高8，与任务槽相同。上传超过4ms时字节预算减半，最低1字节；低于2ms时增加256KiB，最高8MiB，与执行器输入上限相同。落在区间内则保持不变。呈现等待不参与调节，否则固定刷新间隔会被当成过载。

上传队列按分区保持顺序。本帧至少送出队列里的第一份，即使它大于字节预算，避免预算缩到比单个网格还小之后永远不前进。后续份数必须同时放进剩余字节和每帧8份的硬上限。没送出的分区留在队列里，身份不变。

沿用主干的共享内存池：执行器在复制输入前预留输入、工作及输出空间和任务元数据，归入不可驱逐的执行器类。单份预留超过上限时直接失败，世界保持原样；临时不足时背压，下一帧重试。取消中的工作仍持有租约，直到工作及其输入／输出实际释放；成功结果可将预留转入世界或网格类。没有额外的独立账本。任务槽和输入／输出字节硬上限仍先于共享预留检查。

内容包的同步网格路径也按每帧分区预算重建；传入0不重建，剩余分区留待以后帧。离屏的完整串行参考接口保持不变。

## 二、同一次运行的三列耗时

窗口汇总在原有帧间隔之外，另报三次均值，单位微秒：

| 字段 | 计什么 |
|---|---|
| cpu_us | 主线程上接纳和安装生成、网格的时间 |
| upload_us | 建立几何缓冲的时间 |
| present_us | 编码并呈现成功的那一段 |

逻辑步不计入这三列。呈现失败的帧不进入present_us。这些是主机墙钟耗时，upload_us不代表GPU传输完成耗时，present_us包含获取交换链图像时可能发生的等待，不是GPU计时查询。

```sh
cargo run --release -p torse-client --locked -- --window --autoplay --frames 1600 --radius 4
```

汇总行含`cpu_us`、`upload_us`、`present_us`。发布构建的对照还没有重跑。

另有一次调试构建的窗口运行，数字只说明这条路径能跑完，不能拿来和发布构建的帧时比较。环境：Windows，debug profile，Vulkan，Mailbox，NVIDIA GeForce RTX 4050 Laptop GPU，半径1，40帧，无自动飞行。

```sh
cargo run -p torse-client --locked -- --window --frames 40 --radius 1
```

| 项 | 值 |
|---|---|
| 帧数 | 40 |
| 结束时分区与网格 | 9/9 |
| 重建与上传 | 9/9 |
| cpu_us | 973 |
| upload_us | 708 |
| present_us | 6107 |
| 平均帧间隔 | 7967微秒 |
| 背压 | 4 |
| 输出预留峰值 | 24814272字节，上限33554432 |

背压出现时输出预留接近上限，拒绝的是执行器字节硬上限，不是把预算降到0。

## 三、自动验证

在仓库根目录运行：

```sh
cargo test -p torse-client --locked scene::pace
cargo test -p torse-client --locked scene::background
cargo test -p torse-client --locked window::tests
cargo test -p torse-client --locked foreground_visuals_honor
cargo clippy -p torse-client --all-targets --locked -- -D warnings
```

| 场景 | 结果 |
|---|---|
| 0、1、2、8、65、128个并行度 | 工人数分别为1、1、1、7、64、64 |
| 连续快帧 | 分区限额停在8，上传字节停在8MiB |
| 一次过载 | 分区限额和上传字节各减半 |
| 恰好落在目标或一半 | 预算不变 |
| 连续过载 | 分区限额和上传字节降到1，之后不再下降 |
| 过载后再一帧很快 | 分区限额加1，上传字节增加256KiB |
| 三份上传里只有第一份放得下 | 送出第一份，后两份按原顺序留下 |
| 30份1字节 | 本帧最多8份 |
| 第一份大于预算 | 仍送出这一份，不送第二份 |
| 共享执行器类只能容纳一份任务预留 | 第二份记背压，执行器任务数保持1，已装载分区的修订不变，邻区仍未装载 |
| 共享执行器类只能容纳队列元数据 | 单份任务预留失败，不接纳任务，已装载分区的修订和格数不变 |
| 1与4工人、重定心、网格失效 | 完成后执行器类只剩队列预留，场景销毁后全部释放 |
| 同步场景预算为0或1 | 分别不重建或只重建一个；分帧完成后的几何与完整串行结果一致 |

以上命令可独立复跑。

## 四、本地审查修正与验证

在最新主干上重新检查时，修正了两处遗漏：独立执行器账本与共享预算重复，且取消任务会过早释放该独立记账；同步内容包网格忽略了传入的帧预算。现在直接沿用共享执行器租约，并给同步网格加上与窗口相同的分区限额。新增同步预算回归在修复前失败，修复后通过。

客户端101项测试、全工作区测试、全工作区Clippy（禁止警告）和格式检查通过。共享预算覆盖单任务容量、暂时背压、不可满足的预留及场景销毁后的释放。

另执行一次真实窗口检查：Windows，debug profile，Vulkan，Mailbox，NVIDIA GeForce RTX 4050 Laptop GPU。此结果用于验证接线与进度，不作为release性能改进结论，也不与历史40帧结果比较。

```sh
cargo run -p torse-client --locked -- --window --autoplay --frames 240 --radius 2
```

本次窗口成功呈现240帧，流式中心变更2次，结束时25分区／25网格，重建85次／上传85次，10次编辑成功。主线程流式与网格工作均值1320微秒，几何上传771微秒，编码与呈现3156微秒；平均帧间隔5398微秒，最大21278微秒。执行器任务峰值7（上限8），输入预留峰值2613288字节（上限8388608），工作与输出预留峰值26413816字节（上限33554432）。共享逻辑内存峰值134003541字节，低于默认512MiB；该值不是进程RSS或GPU显存。

未补测release对照、GPU传输完成时延或长期帧时分布；自动测试使用不同预算覆盖收缩逻辑，以上单次窗口结果不证明所有设备上的帧时上限。
